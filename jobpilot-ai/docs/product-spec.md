# 화면 및 상호작용 기획

## 핵심 사용자 시나리오

1. 김개발은 프로필에 희망 직무, 기술, 프로젝트, 교육·자격증을 등록한다.
2. SaraminDATA에서 동기화된 사람인 IT 공고가 기술 사전과 요구사항으로 구조화된다.
3. 매칭 엔진이 공고의 필수/우대 조건과 회원 근거를 비교한다.
4. 김개발은 `지원 조건 충족 가능` 공고의 **왜 이 결과인가**를 요구사항 단위로 확인한다.
5. AWS 배포 근거가 없음을 보고 K-디지털 훈련 또는 배포 프로젝트를 관심 등록한다.
6. 채용 마감과 훈련 신청 마감이 플래너에 자동 생성된다.

## UI 원칙

### 1. 추천 카드

- 반드시 출처 배지, 원문 링크, 마감일을 표시한다.
- `현재 근거 부족`은 기본 개인 추천 카드에 노출하지 않는다.
- 카드의 주 정보는 회사명·직무보다 먼저 ‘지원 준비도 등급과 이유’다.

### 2. 매칭 상세 Drawer

- 화면 우측 패널에 공고 상세를 열어 목록 탐색 맥락을 유지한다.
- 각 행은 공고 요구사항, 회원 근거, 상태, 다음 행동을 보여 준다.
- `DIRECT`: 프로젝트·자격증·교육·GitHub 중 직접 근거가 있음
- `RELATED`: 연관 경험은 있으나 공고 표현과 직접 연결하려면 설명 보완이 필요함
- `MISSING`: 보유 근거가 없음
- `CHECK_REQUIRED`: 모호하거나 사용자가 사실 여부를 확인해야 함

### 3. 관심과 플래너

- 북마크는 `user_interests`를 만든다.
- 일정은 그 결과일 뿐 원본이 아니다. 따라서 플래너에서 일정을 지워도 원본 공고의 관심 상태·공고 데이터는 유지한다.
- 마감일만 있는 공고는 종일 이벤트 한 건, 교육은 신청 마감 및 수강 기간 이벤트를 만든다.

## 등급 판단의 안전선

`경력 n년 이상`, `특정 지역 상주`, `필수 자격증`처럼 원문에 명시된 제한과 충돌하면 `DIFFICULT_NOW` 후보가 된다. 부족 요건이 한두 개면 `CHALLENGE_AFTER_GAPS`, 필수 요건이 근거로 대부분 확인되면 `APPLY_NOW`로 분류한다. 파싱이 애매하면 `CHECK_REQUIRED`로 남기고 사용자가 사람인 원문을 보도록 한다.

LLM이 쓰는 범위는 다음으로 제한한다.

- 공고 문장으로부터 기술·요건 후보 추출
- 저장된 요구사항/근거를 사용자가 읽기 쉬운 코멘트로 정리
- 다음 행동을 문장화

LLM이 하지 않는 일은 다음과 같다.

- 합격 확률 산정
- 없는 프로젝트·자격·경험 생성
- 공고 원문보다 우선하는 최종 자격 판정
